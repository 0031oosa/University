# Сбор и обезличенная аналитика открытых дроп-реквизитов

Исследовательский конвейер: сбор публичных списков дроп-реквизитов (карты /
телефоны СБП) → нормализация → обезличенное хранение → агрегатная аналитика.
Практикум магистратуры «ИИ и МО». Полная постановка — см. `docs/ТЗ.md`.

## Установка

```bash
python -m pip install -r requirements.txt
```

Python 3.10+.

## Запуск

### 1. Демо-аналитика (без сети, без реальных ПДн)

```bash
python analyze.py --demo
```

Генерирует 300 синтетических Luhn-валидных записей (фиксированный seed=42)
и строит 4 графика в `report_assets/`:

1. `fig1_payment_systems.png` — распределение по платёжным системам;
2. `fig2_top_bins.png` — топ БИН-групп;
3. `fig3_operators.png` — распределение по операторам СБП (по префиксу);
4. `fig4_monthly_dynamics.png` — динамика пополнения списка по месяцам.

### 2. Демо-прогон сбора (парсинг → нормализация → хранение → маскированный CSV)

```bash
python scraper.py --demo --export-csv drops_masked.csv
```

HTML не запрашивается по сети — используется встроенный синтетический
образец разметки. Полные реквизиты попадают только в локальный
`drops.sqlite3`; в `drops_masked.csv` — исключительно маскированные значения.

### 3. Реальный сбор (только после согласования с научным руководителем)

```bash
python scraper.py --url https://<источник>/<раздел> --db drops.sqlite3 --export-csv drops_masked.csv
```

Перед реальным запуском обязательно:

- подогнать `SELECTORS` и `COLUMN_ALIASES` в `scraper.py` под фактическую
  разметку целевой страницы;
- убедиться, что раздел действительно публичный (без логина/капчи);
- проверить `robots.txt` целевого сайта для используемого User-Agent —
  `PoliteFetcher` делает это автоматически и поднимает `RobotsDisallowedError`,
  если обход запрещён;
- получить согласование постановки задачи у научного руководителя.

#### Обход всей истории (пагинация/архив)

```bash
# Режим 1 (по умолчанию): следовать по ссылке "следующая страница"
# (SELECTORS['next_page'] — подогнать под вёрстку пагинации сайта)
python scraper.py --url https://<источник>/<раздел> --all-pages \
  --db drops.sqlite3 --export-csv drops_masked.csv

# Режим 2: перебор ?page=N, если явной ссылки "следующая" нет
python scraper.py --url https://<источник>/<раздел> --all-pages \
  --pagination-mode query-param --page-param page --max-pages 500 \
  --db drops.sqlite3 --export-csv drops_masked.csv
```

Каждая страница по-прежнему идёт через `PoliteFetcher.fetch()` — тот же
троттлинг (≥2 c), backoff и проверка `robots.txt`, что и для одиночного
запроса; при запрете robots.txt (`RobotsDisallowedError`) обход
останавливается немедленно. `--max-pages` — предохранитель от
бесконечного обхода; при сетевой ошибке или отсутствии дальнейших
страниц обход завершается штатно, всё уже собранное — сохраняется.

### 4. Мониторинг новых записей с алертом на почту (`monitor.py`)

Одноразовый CLI под внешний планировщик: собирает актуальный снимок,
сравнивает с уже сохранённым в SQLite по ключу идентичности (SHA-256 от
нормализованной пары `card, phone`), добавляет только новые записи
(`first_seen_at` фиксируется в момент первой вставки) и присылает
обезличённый алерт.

```bash
# Проверка на синтетике, без сети и без реальной отправки:
python monitor.py --demo --dry-run

# Реальный источник (после согласования и подгонки SELECTORS в scraper.py):
python monitor.py --url https://<источник>/<раздел> --db platshield_data.sqlite

# Локальный HTML-файл вместо сети (тесты/отладка разметки):
python monitor.py --html-file page.html --db platshield_data.sqlite --dry-run
```

Ключевые флаги:

| Флаг | Назначение |
|---|---|
| `--url` / `--demo` / `--html-file` | ровно один источник снимка (взаимоисключающие) |
| `--db` | путь к SQLite (по умолчанию `platshield_data.sqlite`) |
| `--dry-run` | печатает тему и тело письма в stdout вместо отправки |
| `--always-send` | отправлять письмо, даже если новых записей 0 |
| `--seed`, `--n` | параметры синтетики для `--demo` |

При 0 новых записей и без `--always-send` письмо не отправляется и не
печатается — это и есть идемпотентность повторного запуска по расписанию.

#### Переменные окружения (SMTP-креды — только так, не в коде/репозитории)

| Переменная | Обязательна | Назначение | Пример |
|---|---|---|---|
| `SMTP_HOST` | да | адрес SMTP-сервера | `smtp.yandex.ru` |
| `SMTP_PORT` | нет (по умолч. `587`) | порт SMTP | `587` |
| `SMTP_USERNAME` | нет | логин SMTP (если нужна аутентификация) | `alerts@example.org` |
| `SMTP_PASSWORD` | нет | пароль/app-password SMTP | `********` |
| `SMTP_USE_TLS` | нет (по умолч. включено) | STARTTLS; `0`/`false` — отключить | `1` |
| `ALERT_FROM_EMAIL` | да | адрес отправителя | `alerts@example.org` |
| `ALERT_TO_EMAILS` | да | получатели через запятую | `you@example.org,supervisor@example.org` |

Без `--dry-run` при отсутствии `SMTP_HOST` / `ALERT_FROM_EMAIL` /
`ALERT_TO_EMAILS` скрипт завершится ошибкой ещё до попытки соединения —
это осознанное поведение (нет способа отправить письмо «в никуда» или по
захардкоженным адресам).

#### Пример cron (Linux/macOS)

```cron
# Проверка каждые 30 минут, лог — в отдельный файл (тоже без сырых ПДн)
*/30 * * * * cd /path/to/project && \
  SMTP_HOST=smtp.example.org SMTP_USERNAME=alerts@example.org SMTP_PASSWORD=*** \
  ALERT_FROM_EMAIL=alerts@example.org ALERT_TO_EMAILS=you@example.org \
  /path/to/venv/bin/python monitor.py --url https://<источник>/<раздел> \
  --db /path/to/project/platshield_data.sqlite >> monitor.log 2>&1
```

На практике секреты в cron лучше не хранить в самой crontab-строке, а
подключать через `EnvironmentFile=`/`.env`, читаемый только владельцем
(`chmod 600`), либо через systemd-timer с `Environment=`/`EnvironmentFile=`
в unit-файле.

#### Пример Windows Task Scheduler

Создать задачу через `schtasks` с триггером по расписанию, переменные
окружения задать на уровне пользователя/задачи (не в коде):

```powershell
$env:SMTP_HOST = "smtp.example.org"
$env:SMTP_USERNAME = "alerts@example.org"
$env:SMTP_PASSWORD = "***"
$env:ALERT_FROM_EMAIL = "alerts@example.org"
$env:ALERT_TO_EMAILS = "you@example.org"

schtasks /Create /TN "P2P-drops monitor" /SC MINUTE /MO 30 `
  /TR "python.exe D:\path\to\project\monitor.py --url https://<источник>/<раздел> --db D:\path\to\project\platshield_data.sqlite" `
  /RU "%USERNAME%"
```

Для хранения `SMTP_PASSWORD` предпочтительнее переменные окружения
пользователя (`setx`, задаются один раз в системе), а не значения внутри
самой команды `/TR` — так секрет не попадает в историю Task Scheduler.

### 5. Олл-тайм дашборд и статический экспорт графиков (`visualize.py` + `dashboard.py`)

`visualize.py` — общий модуль данных и агрегатов (KPI, кумулятивный рост,
календарный хитмап, bank×system, treemap, доли операторов во времени,
тренд со скользящим средним). Его использует и интерактивный дашборд, и
офлайн-экспорт в PNG — так что оба всегда показывают одни и те же цифры.

```bash
# Интерактивный дашборд (Streamlit + Plotly), синтетика:
streamlit run dashboard.py -- --demo

# Тот же дашборд на реальной локальной БД:
streamlit run dashboard.py -- --db platshield_data.sqlite
```

В сайдбаре: переключатель источника данных (демо/SQLite), фильтры по
периоду, платёжной системе, банку и оператору СБП — все графики
пересчитываются реактивно, KPI-плашки сверху всегда показывают all-time
итоги по всей базе (независимо от фильтров).

```bash
# Статический экспорт тех же графиков в PNG (без Streamlit — для отчёта):
python visualize.py --demo --out-dir report_assets
python visualize.py --db platshield_data.sqlite --out-dir report_assets
```

Создаёт `fig5_cumulative_growth.png` … `fig10_rolling_trend.png` в
дополнение к `fig1`–`fig4` из `analyze.py --demo`.

Как и везде в проекте: `visualize.load_dataframe()` физически не выбирает
колонки `card`/`phone` из SQLite (только `card_bin`, платёжную систему и
3-значный префикс телефона через `substr()` прямо в SQL-запросе) — так что
ни в дашборде, ни в тултипах, ни в PNG-экспорте полный PAN или телефон
в принципе не может появиться, даже случайно.

Атрибуция банка по БИН — без подключённой внешней БИН-базы (см.
`scraper.BinLookup`) на реальных данных банк-бакет равен самому БИН
(`"БИН 400000"`); в `--demo` используется небольшая иллюстративная таблица
соответствий только для того, чтобы показать дашборд с содержательной
группировкой — это не настоящие банки.

### 6. Признаки для ML-детекции мулов (`build_features.py`)

Строит по одной строке на уникальную сущность (номер карты либо номер СБП,
а не на строку-транзакцию): частоту повторного появления, разброс во
времени, число разных площадок/зеркал/шлюзов, связность через общие
площадки с другими сущностями. Обоснование признаков — в докстринге
модуля и в `ARCHITECTURE.md`.

```bash
python build_features.py --db platshield_data.sqlite,platshield_gsheets_test.sqlite,platshield_archive_local.sqlite \
  --export-csv entity_features_masked.csv
```

Как и везде в проекте: сам номер карты/телефона используется только для
группировки внутри процесса, в экспортируемый CSV попадает только
`entity_hash` (SHA-256) — восстановить исходный номер из него практически
невозможно, а для обучения модели он не нужен (признаки строятся по
группировке, а не по значению номера).

### 7. Сборка отчёта по практике (`report/`)

Node.js-тулинг под форматирование кафедры (Times New Roman 12pt, интервал
1.15, поля/автополе оглавления — см. `docs/ТЗ.md` и `report/build_report.js`).
Графики в `report_assets/`/`feature_assets/` должны быть уже сгенерированы
(разделы 5 и 6 выше) — сборщик их только вставляет, сам не считает.

```bash
cd report
npm install
node assemble_report.js
```

Результат — `Отчёт_по_практике.docx` в корне репозитория (путь вывода не
зависит от того, откуда запущен скрипт).

## Ответственное обращение с данными (152-ФЗ)

- Модуль работает только с публичными страницами, без обхода авторизации,
  капчи или иных технических ограничений.
- `PoliteFetcher` соблюдает `robots.txt`, ограничивает частоту запросов
  (≥2 c между запросами), использует честный `User-Agent` с контактом и
  экспоненциальный backoff при ошибках/`429`.
- Полные номера карт (PAN) и телефонов сохраняются **только** в локальном
  SQLite-файле (`Storage`) — он не должен публиковаться, коммититься в
  репозиторий или передаваться третьим лицам.
- Во все внешние артефакты — логи, консольный вывод, CSV-экспорт
  (`Storage.export_masked_csv`), графики (`analyze.py`, `visualize.py`),
  дашборд (`dashboard.py`), e-mail-алерты (`monitor.py`) — попадают
  **только** маскированные (`220220******1234`, `+7(910)***-**-67`) или
  агрегированные значения. Полные реквизиты в них не воспроизводятся.
  `visualize.load_dataframe()` физически не выбирает колонки `card`/`phone`
  из SQLite — только производные безопасные поля (см. раздел про дашборд
  выше), поэтому утечка полного PAN/телефона в дашборд или PNG-экспорт
  невозможна даже при ошибке в коде графиков.
- `monitor.py` не сверяет собранные данные с внутренними/банковскими
  системами и не деанонимизирует людей — работает только с собственными
  ранее собранными открытыми данными и ключом идентичности
  (`identity_hash`), который не покидает локальную БД.
- Инструмент не перепубликует и не передаёт персональные данные третьим
  лицам; назначение — исследовательский датасет для задач детекции
  счетов-посредников («мулов») методами ML.
- Реальный сбор данных выполняется только после согласования постановки
  задачи с научным руководителем.
