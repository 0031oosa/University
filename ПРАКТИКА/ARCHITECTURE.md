# Архитектура

Этот документ описывает, как устроен конвейер сбора и обезличенной аналитики
дроп-реквизитов: из каких модулей он состоит, как данные проходят через них,
какая схема хранения используется и какие design-решения за этим стоят.
Постановка задачи и ограничения — в `docs/ТЗ.md`, инструкции по запуску — в
`README.md`.

## Данные: путь от источника до отчёта

Ключевое правило, которое проведено через весь конвейер: **полные
card/phone/ФИО существуют только в SQLite и в памяти процесса, который их
только что нормализовал**. Ни один модуль, отдающий данные наружу (файл,
график, письмо), не имеет доступа к сырым колонкам — либо потому что не
выбирает их из SQL-запроса вообще (`visualize.py`), либо потому что
единственная функция, которой разрешено писать во внешний файл,
маскирует значения перед записью (`export_masked_csv`).

## Модули

| Модуль | Отвечает за |
|---|---|
| `scraper.py` | `PoliteFetcher` (robots.txt, троттлинг, backoff), Луна-валидация, извлечение BIN, определение платёжной системы, нормализация телефона, маскирование, демо-генератор синтетики |
| `sheet_collector.py` | Сбор с живого JSON API platshield.com: обнаружение листов, постраничный обход вкладок, нормализация строки источника, `SheetStorage` (SQLite + `export_masked_csv`) |
| `ingest_local_archive.py` | Тот же конвейер нормализации для CSV, которые пользователь выгрузил и передал сам (не сетевой сбор) |
| `monitor.py` | Периодический CLI: сравнивает новый снимок с уже сохранённым по `identity_hash`, шлёт обезличенный e-mail только по новым записям |
| `analyze.py` | Агрегаты и 4 статических графика (платёжные системы, BIN, операторы, помесячная динамика); демо-режим на синтетике |
| `visualize.py` | Общий модуль агрегатов для дашборда и статического экспорта: KPI, кумулятивный рост, календарный хитмап, BIN×система, доли операторов во времени, скользящее среднее |
| `dashboard.py` | Интерактивный Streamlit/Plotly дашборд поверх `visualize.py` — те же цифры, что и в статических графиках |
| `build_features.py` | Признаки уровня сущности (card/phone) для ML-детекции мулов: повторяемость, разброс во времени, связность через общие площадки |

## Схема хранения

Две таблицы, сознательно не смешанные:

- **`drops`** (`scraper.py`) — учебная модель под демо-данные и первую
  версию сборщика: `card`, `card_bin`, `payment_system`, `phone`,
  `added_at`, `source_note`.
- **`sheet_drops`** (`sheet_collector.py`) — реальная схема, которую отдаёт
  источник: помимо card/phone несёт ФИО, площадку, зеркало (URL),
  платёжный канал (URL), название банка. Схема шире и не похожа на
  `drops`, поэтому это отдельная таблица, а не попытка втиснуть новые поля
  в старую.

Дедупликация в `sheet_drops` — по **позиции строки в источнике**
(`sha256(sheet_slug|tab_index|row_number)`), а не по значению card/phone.
Один и тот же номер карты законно повторяется в разных строках источника
(разные площадки, разные даты) — если дедуплицировать по значению, это
схлопнёт записи и потеряет сигнал повторяемости, который для задачи
детекции «мулов» как раз может быть полезным признаком. Дедуп здесь нужен
только для идемпотентности повторного запуска сборщика, а не для
«схлопывания» повторов данных.

## Обезличивание: не одна проверка, а несколько независимых слоёв

Первая версия маскирования закрывала только card/phone/ФИО в их «родных»
колонках. При сверке реального экспорта (перекрёстное сравнение с уже
известными полными значениями по всему датасету) обнаружилось, что поля
источника ненадёжны сами по себе: ФИО может оказаться в колонке «банк»,
номер карты — в колонке «URL», а телефон — в query-параметрах легитимного
платёжного URL. Реакция на это — не единственная проверка, а несколько
независимых правил, каждое из которых закрывает свой класс утечки:

1. **Многословность → вероятное ФИО.** Любое значение из 2+ слов в полях
   «банк»/URL маскируется — ценой части легитимных многословных названий
   банков.
2. **Сверка с множеством уже известных ФИО.** Ловит однословные имена без
   фамилии, которые правило (1) пропускает.
3. **10+ цифр в значении → карта/телефон, а не банк.** Отдельная от
   вопроса ФИО проверка — закрывает случай, когда в «банк» или URL
   «убегает» номер карты/телефона целиком.
4. **URL усекается до scheme+домена.** Полная строка URL (с
   query-параметрами) никогда не экспортируется — только то, через какой
   шлюз/зеркало шёл платёж.

Ни одно из этих правил не было предусмотрено заранее — каждое добавлено
по факту находки конкретной утечки на реальных данных и закрыто
регрессионным тестом на том же примере, который её обнаружил (см.
`tests/test_sheet_collector.py`).

## Аналитика: общий модуль агрегатов

`visualize.py` — единственное место, где вычисляются агрегаты (KPI,
кумулятивный рост, календарный хитмап, доли по банкам/операторам,
скользящее среднее). И `dashboard.py`, и статический экспорт в
`report_assets/` вызывают одни и те же функции — это исключает ситуацию,
когда дашборд и отчёт молча расходятся в цифрах из-за двух независимых
реализаций одной и той же агрегации.

Данные могут собираться из нескольких SQLite-файлов одновременно
(`--db a.sqlite,b.sqlite,c.sqlite`) — так сведены воедино три независимых
источника без создания четвёртой копии данных.

Отдельно учтено, что реальный сбор шёл не непрерывным мониторингом, а
периодическими снимками по отдельным месяцам («островами»): агрегаты по
времени (`new_per_period`, `rolling_trend`) не заполняют нулями периоды
без наблюдений — период либо есть в выборке, либо отсутствует вовсе, но
не «показывает ноль». Иначе график интерпретировал бы многомесячный
разрыв между источниками как настоящий провал активности, которого
данные не подтверждают.

## Признаки для ML (`build_features.py`)

Аналитика выше — описательная, на уровне строк-транзакций. Заявленная
цель проекта (см. `docs/ТЗ.md` п.1.3) — датасет для детекции счетов-
посредников, а это задача уровня сущности (карта/телефон), а не строки.
`build_features.py` строит по одной строке на уникальную сущность:
частоту повторного появления (`occurrences` — прямое следствие того, что
дедуп сделан по позиции строки, а не по значению, см. выше), разброс во
времени (`active_span_days`), число разных площадок/зеркал/шлюзов
(`distinct_casinos`/`distinct_mirror_domains`/`distinct_payment_domains`)
и связность через общие площадки с другими сущностями
(`max_shared_casino_degree`). Экспорт заменяет сам номер на
`entity_hash` — признаки строятся по группировке, а не по значению
номера, поэтому для обучения модели хэша достаточно.

## Тестирование

135 тестов (`python -m unittest discover -s tests`) — без единого
сетевого запроса: постраничный обход и загрузка страниц проверяются на
фиктивном fetcher'е с заранее заданными ответами, дашборд — через
`streamlit.testing.v1.AppTest` в headless-режиме. Отдельный класс тестов
покрывает именно найденные на реальных данных дефекты (утечки в
«банк»/URL-полях, NaN-truthiness при агрегации по BIN, разрывы во
временных графиках) — каждый воспроизводит конкретный пример, который
изначально выявил проблему.

## Известные ограничения

- Атрибуция банка по BIN — по диапазону (Visa/Mastercard/МИР/AmEx), без
  подключённой внешней справочной базы; на реальных данных банк-бакет
  равен самому BIN.
- Атрибуция оператора СБП по префиксу телефона — по небольшой иллюстративной
  таблице, а не по официальному реестру НСС/Роскомнадзора.
- Покрытие по времени неполное и не непрерывное — конкретные месяцы,
  попавшие в выборку, ограничены тем, что было опубликовано источником
  или предоставлено пользователем на момент сбора.
